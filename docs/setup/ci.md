# CIの品質と効率を変更時に確認する

CIのworkflow・起動/選択・runner/cache、CIが使う依存・toolchain・build/test・fixture・成果物処理を変えるときに使います。実行量に影響するアプリ変更やテスト追加も対象です。実行への影響がない文言変更は理由を示し、追加の性能測定を省略できます。全変更で高速化や一律の全観点実験を要求しません。

## 既存の入口と信頼境界

同梱[workflow](../../.github/workflows/check.yml)と[pre-push](../../.githooks/pre-push)は同じ `python3 scripts/check.py` を実行します。この小さいテンプレートは全harnessチェックを毎回実行し、アプリ検査は[project.md](../project.md)で別に定義します。push・pull_request・workflow_dispatchの起動を維持しています。

workflowはcontents:readで、checkoutのcredential保持を無効にしています。PRコードのテスト環境へwrite tokenや本番secretを渡しません。Actionsの版は導入時の方針に従って固定・更新し、起動を確認します。

配布を追加する場合はtest/buildとpublishを分け、実際にbuildしたSHA/hashを保存します。branchが進んだだけで旧artifactを新SHAとして扱いません。PRの任意コードをtrustedなmerge/publish判定として実行せず、判断側を既定branchの確認済みrevisionに置きます。

導入先で重い検証を選択実行する場合は、rename/delete/mode変更、混在、unknown、不完全履歴を含めて検証し、hook/CI/coordinatorに判定を重複実装しません。選択不能は全量実行へ戻し、必要な全量実行も不能なら未達です。必須検査の失敗・中断・時間切れ・欠落、正当に空と確認できない0件を成功に変えません。キャッシュは再計算可能な補助データとし、成果物の同一性・生成元と別に確認します。

## 変更ごとの判断と記録

新しい台帳を作らず、[start-work](../../.agents/skills/start-work/SKILL.md) → 既存Issueでの計画/実装 → [PR欄](../../.github/pull_request_template.md) → [finish-work](../../.agents/skills/finish-work/SKILL.md)・独立レビューに同じ根拠をつなぎます。

| 時点・担当 | 必要な判断 |
| --- | --- |
| 計画・writer | 影響する起動回数、待ち/準備/検査/保存と守る検証義務を特定する。実行影響なし、固定入力/条件が一致する既存証拠の再利用、有限比較が必要、から理由付きで選ぶ。比較前に基準/候補、指標、品質/採否、回数/時間/費用上限、停止/復元条件を決める |
| 実装・writer | 必須検査、対象ID、入力/成果物の同一性、失敗伝播を保ち、通常検査と必要な比較を実行する。正常系、意図的な失敗検知、切戻しを変更に応じて確認し、失敗/取消し・測定省略理由・未達も残す |
| 固定レビュー・独立reviewer | 測定/再利用/省略理由、品質同等性、主張と実条件、劣化時の担当/復旧を評価する。運用手順の変更は欄の存在だけで成立とせず、実変更への適用または有限で戻せる試行の結果を読む |
| 統合・後続owner | 固定版のCIと残条件を読む。統合前の問題は当該Issue/PR、統合後の退行は元変更へ結ぶ不具合管理に担当・調査/切戻し・再確認条件を残す |

測定時はsource/base、workflow/checker、tool/runner、入力種別、cache条件、実行数を特定します。通常・コールド・ウォーム・失敗・連続更新・依存障害を必要な範囲で分け、失敗/取消しを除外しません。最初の有用な結果、必須検査完了、全ジョブの総実行時間、転送/保守負担は別の指標です。並列時間を単純加算せず、実課金が不明なら費用は未測定にします。小標本や局所テストの差をCI全体・別環境へ外挿しません。

過去の成功を再利用する場合も、source・関連依存・設定・tool・環境・外部情報の鮮度を照合します。別runner/cache条件の短縮率、古い成果物、入力不明の成功は現在の証拠にしません。再利用理由は同じIssueへ残し、有効な測定を理由なく取り直しません。

必要なテスト追加による時間増加も、保証と許容範囲を説明して評価します。新しいCI入力/環境の変更、実遅延・失敗・品質退行を次の点検契機とし、常駐監視や追加の本人承認gateは作りません。改善効果が未測定ならそのまま記録します。

## 劣化と切り戻し

不正な成功、必要eventの欠落、別対象の取消し、同一性の不一致、説明できない時間/費用の悪化が出たら、担当ownerが該当施策を止めて原因を確認します。通常のIssue branch/PRで既知の構成へ戻し、必要な全量・cacheなし・正常/失敗入力で復帰を確認します。必須検査・独立レビュー・保護は維持し、公開/データ変更の副作用は専用の復旧条件で扱います。
